# Scenarios: greenfield, brownfield, ambiguous

How this backend is approached in three common situations. Each scenario uses the same three steps:

1. **Decomposition** — split the work, name constraints, decide what is in or out.
2. **Execution** — implement in an order that keeps the system runnable.
3. **Validation** — prove the result against acceptance criteria, tests, and the HTTP contract.

The service itself is described in [`1.Architecture.md`](1.Architecture.md). The brief and decisions are in [`0.Requirements-analysis.md`](0.Requirements-analysis.md). The committed API is [`openapi.json`](openapi.json).

---

## 1. Greenfield

**Situation:** a new URL shortener. The workspace had a Java 21 / Spring Boot 4.1 scaffold and nothing else: no schema, no API, no click path.

### Decomposition

Turn the brief (create, redirect, details, analytics, unknown codes, invalid URLs, database errors, optional expiry) into:

| Slice | What was decided |
| --- | --- |
| Use cases | Four HTTP operations: `POST /api/v1/short-urls`, `GET /{code}`, `GET /api/v1/short-urls/{code}`, `GET .../analytics` |
| Shape | One JAR, one database. No extra product services. |
| Data | `short_link` + `click_event`. Unique `code`. No IP column. |
| Redirect | 302 + `Cache-Control: no-store` so every click reaches the server. |
| Codes | 7-character base62, `SecureRandom`, unique constraint + bounded retry. |
| Clicks | Async on a bounded in-process executor; insert + `click_count += 1` in one transaction. |
| Profiles | `local` = H2; `prod` = PostgreSQL via env vars. Flyway owns the schema. |
| Out of scope for v1 | Auth, custom aliases, update/delete/list-all, cache, Kafka. |

Phases: core domain and schema → HTTP API → hardening (validation, rate limits, errors) → tests and contract → deploy files.

### Execution

- Layering: controller → service → repository. Controllers map HTTP; services own rules; Flyway owns tables.
- `create` is not one big `@Transactional` so a unique-constraint collision can be retried.
- `resolve` is one indexed lookup, then the 302. The click is submitted to a queue of 1000 (`AbortPolicy`, never `CallerRunsPolicy`).
- Cross-cutting last: correlation id, 8 KB body cap, security headers, per-IP rate limits, RFC 7807 errors.
- Prod packaging after the API was stable: Docker image defaults to `prod`; Ingress → Service → 2 pods → PostgreSQL.

### Validation

| Check | How |
| --- | --- |
| Acceptance criteria | Written before code; mapped in `0.Requirements-analysis.md` Part K |
| Unit tests | Validator, generator, rate limiter, services (inject a fake `Executor` / `Clock`) |
| Integration tests | MockMvc + H2 + Flyway: create, redirect, expiry, 404/410, analytics, collision retry, concurrent redirects, full click queue, database outage |
| Coverage | JaCoCo gate: 80% line coverage on `service.impl` and `util` |
| Contract | `OpenApiContractTest` fails if the live spec drifts from `docs/openapi.json` |
| Errors | Every failure is `application/problem+json` with a stable `code` and `traceId` |

## 2. Brownfield

**Situation:** this service already runs. A change must land without breaking existing clients or the redirect path.

Examples that fit the current code: a cache in front of `resolve` / analytics, Kafka instead of the in-process click queue, authentication, custom aliases.

### Decomposition

Freeze what callers already depend on, then isolate the change.

| Frozen | Why |
| --- | --- |
| Paths and status codes (`201`, `302`, `404`, `410`, `429`, `503`) | Existing clients and the committed OpenAPI file |
| Error envelope (`code`, `traceId`) | Callers branch on `code` |
| Unique `code` + Flyway history | Do not rewrite V1; add `V2__...` |
| Redirect must not wait on extra I/O | NFR: click (and any new side work) stays off the 302 |

Then ask only the questions the change needs:

- **Cache:** what is the key, TTL, and invalidation when a link expires? Analytics is not called often today, so a cache is optional until live stats exist.
- **External queue:** click write is still one insert + increment. Kafka is justified only if more work is added around each click, or the in-process queue of 1000 is no longer enough.
- **Auth:** which routes are public (`GET /{code}` must stay public) vs protected (create, details, analytics)?
- **Custom alias:** new uniqueness rule, reserved-word list, and a new Flyway column or table — not a silent change to random codes.

Blast radius on this codebase: rate limits and the click queue are **per pod**; the database is shared. A brownfield change that assumes a single instance will be wrong at `replicas: 2`.

### Execution

1. Add a migration if the schema changes; keep Hibernate on `validate`.
2. Introduce the new piece behind an existing seam (`LinkService`, `ClickService`, `ClickWriter`, or the executor bean) so controllers stay thin.
3. Do not put the new I/O on the request thread of `GET /{code}`.
4. Carry config as env vars / ConfigMap / Secret, same as `DB_URL` and `APP_BASE_URL`.
5. Leave `docs/openapi.json` unchanged unless the HTTP contract actually changes; if it does, version or add fields as additive.

### Validation

- The existing suite must stay green (`mvnw verify`, including the OpenAPI drift test).
- Add tests at the same level as the seam you touched: unit for the new policy, integration for the HTTP status and the Flyway migration.
- Re-run the hard cases if the change sits near them: concurrent redirects, saturated click queue, database outage, expired link still readable on details.
- If the public contract changed, update `docs/openapi.json` deliberately (`openapi.update=true`) and review the diff.

## 3. Ambiguous

**Situation:** the brief named the features but not the rules. 301 vs 302, same URL vs new code, auth, what “analytics” stores, expiry as TTL vs timestamp, scale, and what a database error should look like were all open.

### Decomposition

Do not start with code. List each ambiguity, why it changes the design, and a default if nobody answers.

| Ambiguity | Why it matters | Default used |
| --- | --- | --- |
| 301 vs 302 | Cached 301 skips the server; analytics and expiry break | 302 + `no-store` |
| Auth / ownership | Who can read details and analytics | None; public by code; auth later |
| Analytics contents | Schema and privacy | Timestamp, referrer, user agent; no IP |
| Expiry shape | API and whether a scheduler is needed | Absolute UTC instant, checked at request time |
| Scale | Cache, Kafka, pool sizes | Prototype; in-process click queue |
| Invalid URL / private hosts | Security vs local testing | Strict in prod; private hosts allowed on `local` |
| Database errors | Client retry vs leak | Generic `503` / `500` + `Retry-After` on 503 |

Write the brief separately from the decisions (`0.Requirements-analysis.md` Parts A vs B–D). Decide the ones that affect the contract (redirect status, auth, click recording) before coding. Everything else uses the documented default.

### Execution

Implement only what was decided or defaulted. When two implementations would both “work”:

- Prefer the option that keeps `GET /{code}` small (async clicks, no `@Async` self-invocation, no write on the request thread).
- Prefer database constraints over app-only uniqueness.
- Prefer request-time expiry over a background job.
- Record the choice in the architecture decision table so a later brownfield change does not relitigate it by accident.

If a new question appears mid-implementation (for example: does `HEAD` count as a click?), treat it the same way: default, note it, do not silently invent a product rule.

### Validation

An ambiguous requirement is not done until it is testable.

- Each decided rule has an acceptance criterion (unknown code → 404, expired → 410, full queue → still 302, and so on).
- Tests lock the default: collision retry against the real unique constraint, `HEAD` not counted, private hosts rejected in prod-like validation, health `DOWN` when the DataSource fails.
- If a test cannot be written, the requirement is still ambiguous — go back to decomposition rather than shipping an undocumented behaviour.

## How the three relate on this project

| | Greenfield | Brownfield | Ambiguous |
| --- | --- | --- | --- |
| This assignment | The shortener as built | Future cache, Kafka, auth, aliases | The open questions before Phase 1 |
| Decomposition | Features → API, schema, phases | Freeze the contract; isolate the seam | Questions + defaults + pause |
| Execution | Layered monolith, then hardening | Additive migration / bean; keep 302 fast | Implement decisions only |
| Validation | New suite + coverage + OpenAPI | Old suite stays green + targeted new tests | AC exists only after the rule is precise |

Greenfield built the system. Ambiguous work decided its rules. Brownfield is how the listed future enhancements would be added without undoing those rules.

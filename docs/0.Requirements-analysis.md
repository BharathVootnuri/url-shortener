## Part A. Original brief

**Context:** AI-assisted URL shortener for a software engineering interview assignment.

**Stack:** Java and Spring Boot, Angular and TypeScript, PostgreSQL.


| ID  | Original requirement                                 |
| --- | ---------------------------------------------------- |
| O1  | Create short URLs from valid HTTP/HTTPS URLs         |
| O2  | Redirect users from a short code to the original URL |
| O3  | Retrieve URL details                                 |
| O4  | Record and retrieve click analytics                  |
| O5  | Handle unknown codes                                 |
| O6  | Handle invalid URLs                                  |
| O7  | Handle database errors                               |
| O8  | Handle optional link expiration                      |


**Process constraints (brief):** No microservices, Kafka, or extra product infrastructure. Kubernetes manifests in `k8s/` deploy this single app.

## Part D. Implementation decisions

- **D1.** The scope is single-tenant and has no authentication. Because of that, analytics is readable by anyone who knows the code. This is a known limitation, and the design shows where auth would plug in.
- **D2.** The redirect uses **HTTP 302**, so every click reaches the server.
- **D3. URL validation rules:**
  - The scheme must be `http` or `https`, case-insensitive.
  - The URL must have a host.
  - Maximum length is 2048 characters.
  - Userinfo (`user:pass@`) is rejected.
  - `localhost`, loopback, link-local, and private-range IP literals are rejected in **prod**, to prevent abuse and open-redirect-to-internal pivots. They are **allowed in the local profile** so redirects can be tested (`app.url-validation.allow-private-hosts`).
  - The server **never fetches** the target URL, so there is no SSRF surface.
  - The URL is normalized before storing: trimmed, with the scheme and host lowercased. The path and query are preserved exactly.
- **D4.** Short codes are 7-character base62, generated with `SecureRandom`. A unique constraint plus a bounded retry (5 attempts) handles collisions. With 62^7 ≈ 3.5 trillion codes, collisions are negligible at prototype scale.
  - Codes are not sequential, so they can't be enumerated by incrementing.
  - Reserved paths (`api`, `actuator`, `assets`, and similar) are blocked.
- **D5.** Every create call makes a new link. There is no dedupe.
- **D6.** Expiry is an absolute UTC timestamp. It must be in the future at creation and no more than about 5 years ahead. A link is "expired" when `now >= expires_at`, checked at request time, so no scheduler is needed.
- **D7.** Click events are stored one row per click: `short_link_id`, `clicked_at`, `referrer` (truncated to 512), `user_agent` (truncated to 512). **No IP address is stored**, which reduces GDPR/privacy exposure.
- **D8.** Click recording is **asynchronous** and happens after the redirect decision.
  - **Mechanism:** the redirect handler captures the click data (link id, timestamp, referrer, user agent) and hands it to a bounded in-process `ThreadPoolTaskExecutor` (2 core / 4 max threads, queue of 1000, configurable under `app.click-recording.*`). It then returns the 302 immediately. This is an in-JVM executor only, not an external queue.
  - **Failure handling:** a failed write is logged and swallowed. If the queue is full, the click is **dropped** (`AbortPolicy`, never `CallerRunsPolicy`, which would put the write back on the request thread) and a warning is logged. There is no Micrometer counter for drops or failures.
  - **Counter:** a denormalized `click_count` on the link row is incremented atomically (`UPDATE ... SET click_count = click_count + 1`) in the same transaction as the click insert, so the two never diverge.
  - **Consistency:** analytics are **eventually consistent**. A click can take a few milliseconds to appear in details and analytics.
  - **Accepted trade-off:** clicks still queued at a crash or hard kill are lost. A graceful shutdown drains the queue (with a timeout). For a prototype, redirect speed and availability matter more than exact click counts.
  - **Testing:** unit tests inject a fake `Executor`; integration tests use Awaitility to wait for async writes.
- **D9.** All timestamps are stored as `timestamptz` in UTC. The API uses ISO-8601.
- **D10.** Tooling defaults:
  - Java 21 and Spring Boot 4.1.x (already present).
  - **Profiles:** `local` (default) uses in-memory H2 in PostgreSQL-compatibility mode. `prod` (`SPRING_PROFILES_ACTIVE=prod`) uses PostgreSQL, with `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, and `APP_BASE_URL` supplied as environment variables. Config lives in `application.yaml` (shared), `application-local.yaml`, and `application-prod.yaml`.
  - Flyway for migrations, written to run on both H2 (PostgreSQL mode) and PostgreSQL. Hibernate `ddl-auto` is `validate` in both profiles.
  - Root package: `com.bharath.projects.urlshortener`.
  - Prod also sets graceful shutdown, health probes, and `server.forward-headers-strategy: framework` (for Ingress).
  - Docker image and `k8s/` manifests deploy the same JAR (2 replicas). Testcontainers for PostgreSQL is optional. The primary test suite runs on H2.
- **D11.** API versioning is a plain `/api/v1/...` prefix. The redirect lives at the root, `/{code}`.
- **D12.** The deliverable is a runnable prototype with tests, a README, a Docker image, and Kubernetes manifests.

## Part E. API contract


| Method and path                                                | Purpose                                                 | Success                                                                      | Errors                                                           |
| -------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `POST /api/v1/short-urls`                                           | Create a short link. Body: `url`, optional `expiresAt`. | 201 with `code`, `shortUrl`, `originalUrl`, `createdAt`, `expiresAt`         | 400 invalid URL or expiry. 429 rate limited. 503 DB unavailable. |
| `GET /{code}`                                                  | Redirect                                                | 302 with `Location`                                                          | 404 unknown. 410 expired. 503 DB unavailable.                    |
| `GET /api/v1/short-urls/{code}`                                     | Link details                                            | 200 with details, status (`ACTIVE` or `EXPIRED`), `totalClicks`              | 404. 503.                                                        |
| `GET /api/v1/short-urls/{code}/analytics?from=&to=&granularity=DAY` | Click analytics. Range is `[from, to)`, defaulting to the last 30 days. `granularity` is `DAY` or `HOUR`. | 200 with `totalClicks` (all-time), `clicksInRange`, `series[]` (non-empty buckets only), and `topReferrers[]` (max 10) | 400 bad range or granularity. 404. 503.                          |
| `GET /actuator/health`                                         | Health                                                  | 200                                                                          |                                                                  |


**Error envelope (all non-2xx API responses):** RFC 7807-style `application/problem+json` with `type`, `title`, `status`, `detail`, `code` (machine-readable, for example `INVALID_URL`), `traceId`, and field-level `errors[]` for validation. For error responses on `GET /{code}`, the response will be content-negotiated. Browsers get a minimal static HTML error page and API clients get problem+json.

## Part F. Acceptance Criteria

Format is Given / When / Then.

### Feature 1. Create short URL (FR-1, FR-2, FR-3)

- **AC1.1** Given a valid `https://example.com/a?b=1`, when I POST it, then I get 201 with a 7-char base62 `code`, a `shortUrl` built from the configured base, and `createdAt`.
- **AC1.2** Given `ftp://x.com`, `javascript:alert(1)`, `data:`, `//x.com`, an empty string, a missing field, or a URL over 2048 chars, then I get 400 with `code=INVALID_URL` and no row is created.
- **AC1.3** Given a URL containing credentials, localhost, or a private IP, then I get 400.
- **AC1.4** Given a valid `expiresAt` in the future, then it is stored and returned. Given a past or malformed value, then I get 400 `INVALID_EXPIRY`.
- **AC1.5** Given a code collision on insert, then the service retries with a new code. After N failures it returns 500/503 without leaking details.
- **AC1.6** Two creates for the same URL produce two different codes.

### Feature 2. Redirect (FR-4, FR-5)

- **AC2.1** Given an active code, when I GET `/{code}`, then I get 302 with `Location` equal to the original URL, and `Cache-Control: no-store`.
- **AC2.2** Given an unknown code, then I get 404 and no click is recorded.
- **AC2.3** Given an expired code, then I get 410 and no click is recorded.
- **AC2.4** Given a code that doesn't match `[0-9A-Za-z]{7}`, then I get 404 without querying the DB.
- **AC2.5** Given a link that expires at exactly `T`, a request at `T` is treated as expired.

### Feature 3. Retrieve URL details (FR-6)

- **AC3.1** Given an existing code, then I receive original URL, code, short URL, `createdAt`, `expiresAt` (or null), `status`, and `totalClicks`.
- **AC3.2** Given an expired link, then details are still returned with `status=EXPIRED`. Details are readable after expiry, and only the redirect is blocked.
- **AC3.3** Given an unknown code, then I get 404 problem+json.

### Feature 4. Click analytics (FR-7, FR-8)

- **AC4.1** Given N successful redirects, then once async processing completes (within a short, bounded wait), `totalClicks == N` and the sum of the series buckets is N.
- **AC4.2** Each recorded click has a timestamp and truncated referrer and user agent. No IP is stored. The timestamp is captured when the redirect is served, not when the async write runs.
- **AC4.3** Given the click-recording step fails (simulated), then the redirect still returns 302 and the error is logged.
- **AC4.7** Given the click queue is saturated, then the redirect still returns 302 with no added latency, and the click is dropped and logged.
- **AC4.8** Given the redirect handler returns, then it did not wait for the click write (verified by a test using a deliberately slow or blocked recorder).
- **AC4.9** Given a graceful shutdown, then queued clicks are written before the app exits, up to the configured timeout.
- **AC4.4** Given `from > to`, a range over 366 days, or an invalid granularity, then I get 400.
- **AC4.5** Given a link with zero clicks, then analytics return zeros and an empty series, not an error.
- **AC4.6** Concurrent redirects (for example 50 parallel) produce a correct `click_count` with no lost updates.

### Feature 5. Error handling (FR-9, O5–O7)

- **AC5.1** Every error response uses the common envelope and includes `traceId`. No stack traces or SQL appear in responses.
- **AC5.2** Given the DB is down, then API endpoints return 503. The health endpoint reports DOWN. The app recovers without a restart once the DB returns.
- **AC5.3** Given malformed JSON or an unsupported media type, then I get 400 or 415 in the envelope.
- **AC5.4** Given a client exceeding the rate limit on create, then I get 429 with `Retry-After`.

### Feature 6. Expiration (FR-3, FR-5)

- **AC6.1** A link with no `expiresAt` never expires.
- **AC6.2** A link is redirectable before `expiresAt` and returns 410 after, with no restart or job required.
- **AC6.3** The expiry boundary is covered by a test with an injectable clock.

### Feature 7. Angular UI (FR-10)

- **AC7.1** The create form validates the URL client-side, shows server errors inline, and disables submit while the request is in flight.
- **AC7.2** On success it shows the short URL with a copy button, and the details and analytics views are reachable from it.
- **AC7.3** The analytics view shows total clicks and a chart or table, with loading, empty, and error states.
- **AC7.4** A 404 or 410 on the details page shows a human-readable message.

## Part H. Risks

### Security


| Risk                                                                         | Mitigation                                                                                                             |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Malicious destinations** (phishing, malware) used via the service's domain | Scheme allow-list, length cap, rate limiting. A reputation or blocklist check is out of scope and documented.          |
| `javascript:`**/**`data:` **injection**                                      | Strict scheme allow-list. The UI renders URLs as text or links only after validation.                                  |
| **Open redirect abuse** (inherent to the product)                            | Documented limitation. Optionally add an interstitial page later.                                                      |
| **SSRF**                                                                     | The server never fetches target URLs. Private-IP hosts are rejected anyway.                                            |
| **Code enumeration**                                                         | Random 7-char codes (about 3.5T space) and rate limiting on 404s.                                                      |
| **Unauthenticated analytics access**                                         | Documented. Auth is the first post-prototype addition. Analytics exposes no IPs.                                       |
| **Header injection / log injection** via `Location`, referrer, or user agent | Validate and normalize the URL, strip control characters, and truncate stored headers. Use parameterized queries only. |
| **XSS in the Angular UI**                                                    | Angular's default escaping. No `innerHTML` or `bypassSecurityTrust`*.                                                  |
| **CORS misconfiguration**                                                    | An explicit origin allow-list per profile. No wildcard.                                                                |
| **Secrets in repo**                                                          | DB credentials come from environment variables. `.env` is gitignored.                                                  |
| **DoS on create**                                                            | Rate limit, body size limit, and URL length cap.                                                                       |
| **Dependency vulnerabilities**                                               | Pin versions and run `mvn dependency-check` or `npm audit` as part of the final review.                                |


### Reliability


| Risk                                       | Mitigation                                                                                                                                                           |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DB outage breaks all redirects             | Fail fast with a 503. Connection pool timeouts are tuned. An optional small in-memory cache could serve redirects during an outage, but it is deferred (see Part I). |
| Click-write failure breaking redirects     | Writes run on a separate executor thread. Failures are caught and logged, and never reach the request thread.                                                        |
| Slow click writes hurting redirect latency | Async recording on a bounded in-process executor (D8). The redirect never waits on the DB write.                                                                     |
| Lost clicks (queue full, crash before the queue drains) | Bounded queue with drop-and-log, so the redirect is never blocked. Graceful shutdown drains the queue. Documented as an accepted trade-off. |
| Unbounded memory growth from queued clicks | The queue capacity is fixed, so memory is capped.                                                                                                                    |
| Async stale reads                          | Analytics are eventually consistent by design. Tests wait for completion and the README documents this.                                                              |
| Code collisions                            | A DB unique constraint plus bounded retry.                                                                                                                           |
| Clock skew or time-zone bugs in expiry     | UTC `timestamptz` and an injectable `Clock`.                                                                                                                         |
| Connection pool exhaustion                 | Hikari limits and a timeout. A 503 is returned on timeout.                                                                                                           |
| Schema drift                               | Flyway only. Hibernate `ddl-auto=validate`.                                                                                                                          |


### Performance


| Risk                                                | Mitigation                                                                                                       |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Unindexed lookups                                   | Unique index on `code`. Composite index on `click_event(short_link_id, clicked_at)`.                             |
| `COUNT(*)` on a large click table                   | Denormalized `click_count`. Time-series aggregates are bounded by a date-range cap.                              |
| `click_event` growth                                | Documented. A future option is partitioning or rollup tables. Not needed at prototype scale.                     |
| N+1 queries                                         | Explicit queries and DTO projections for analytics.                                                              |
| Hot-row contention on `click_count` for viral links | Acceptable at prototype scale. If it appears, drop the counter and compute from events, or batch the increments. |
| 302 redirects are never browser-cached              | Intentional, so analytics work. Caching (Caffeine) is a later optimization.                                      |

## Part I. Architecture (as built)

A single Spring Boot **modular monolith** (`com.bharath.projects.urlshortener`). In a cluster: Ingress → ClusterIP Service → 2 identical pods → one PostgreSQL. There is no cache, external queue, or in-app API gateway. The only asynchronous piece is an in-process, bounded executor for click recording.

```
 Client
   │ HTTPS
   ▼
 Ingress controller
   │
   ▼
 Service (ClusterIP)
   │
   ├─► Pod 1 (JAR :8080, own rate limiter, own click queue)
   └─► Pod 2 (same)
         │ JDBC
         ▼
    PostgreSQL  (short_link, click_event)
```

Locally there is no Ingress: one process on `:8080` with H2.

**Backend layering:** controller → service → repository. Controllers deal only with HTTP and DTOs. Services hold the rules (validation, expiry, collision retry). Repositories hold the persistence. Entities are never exposed in the API. `GET /{code}` uses `RedirectController` (`HEAD` redirects but is not counted). JSON API is `LinkController`.

**Redirect request flow:**

1. Check the code format. Return 404 immediately if it's malformed.
2. Look up the link by code. Return 404 if it's missing.
3. If `now >= expires_at`, return 410.
4. Capture the click data (timestamp, referrer, user agent) and submit it to the bounded click executor. This does not block. If the queue is full, the click is dropped and logged.
5. Return 302 with `Location` and `Cache-Control: no-store`.
6. *(On the executor thread, later)* In one transaction, insert the `click_event` row and increment `short_link.click_count`. Errors are logged and swallowed.

**Data model (logical):**

- `short_link(id PK, code UNIQUE NOT NULL, original_url NOT NULL, created_at NOT NULL, expires_at NULL, click_count NOT NULL DEFAULT 0)`
- `click_event(id PK, short_link_id FK NOT NULL, clicked_at NOT NULL, referrer NULL, user_agent NULL)`

**Cross-cutting:**

- Config via `application.yaml` and environment variables.
- Structured logging with a correlation ID in the MDC.
- Actuator health.
- Springdoc OpenAPI.
- In-memory rate limiting (three buckets: create, miss, analytics). Per pod; two replicas roughly double the budget.
- Docker image defaults to `prod`. Manifests in `k8s/`.

**Testing strategy:** 282 automated tests — unit tests for rules, `@SpringBootTest` + MockMvc on H2 + Flyway for the ACs, OpenAPI drift test, JaCoCo 80% on `service.impl` and `util`. See [`4.Testing-approach.md`](4.Testing-approach.md).

**Future enhancements:** Redis/Caffeine in front of resolve (if analytics becomes live stats), external queue/Kafka (if click work grows or the in-process queue is not enough), custom aliases, update/delete/list-all, custom expiry, authentication.

## Part J. Decisions

**Resolved:**

1. **Q1, redirect status:** 302.
2. **Q4, authentication:** none.
3. **Q6, analytics depth:** timestamp, referrer, and user agent.
4. **Localhost and private hosts:** accepted in the local profile so redirects can be tested, rejected in prod. This is controlled by per-profile properties.
5. **Database:** H2 for local, PostgreSQL for prod, with separate property files.

6. **Migrations:** Flyway (Testcontainers is optional, since local runs on H2).
7. **Click recording:** asynchronous, using a bounded in-process executor (see D8). Drop and log on overflow; no Micrometer click counters.
8. **`HEAD` on `/{code}`:** 302, not counted as a click.
9. **Analytics** is rate limited (`analytics-per-minute`).
10. **Deploy:** Docker + Kubernetes manifests (Ingress, 2 replicas). Not extra product services.
11. **Package name:** `com.bharath.projects.urlshortener`.

See Part G for the task log and Part K for the review.

### K.2 Security review (manual)

Reviewed: `UrlValidator`, `CorrelationIdFilter`, `RateLimiter` and its interceptor, `SecurityHeadersFilter`,
`RequestSizeLimitFilter`, `GlobalExceptionHandler`, CORS config, both controllers, entity/repository queries, profile configs.

| Area | Result |
| --- | --- |
| Open redirect / scheme abuse (`javascript:`, `data:`, `ftp:`) | Allow-list http/https; ASCII only; `new URI(..)` rejects characters that could break `Location`, so `URI.create` at redirect time cannot fail on stored values |
| Header / log injection | Correlation ids accepted only if `[A-Za-z0-9._-]{1,64}`; referrer and user agent stripped of control characters and truncated; Location built from the validated URL |
| SSRF | Server never fetches targets; numeric-IP tricks, IPv4-mapped IPv6, private, link-local and metadata ranges rejected in prod |
| SQL injection | Spring Data and JPQL with bound parameters only |
| XSS | JSON API; HTML error pages use fixed text and echo nothing; Angular default escaping, no `innerHTML` |
| CORS | Explicit origin list, no wildcard (refused at startup) |
| Information leakage | Generic 5xx bodies; stack traces, messages and binding errors disabled; verified by tests that look for `jdbc`, SQL and class names |
| Secrets | Prod credentials come from environment variables; `.env` files git-ignored |
| Dev tooling in prod | Prod disables Swagger UI, `/v3/api-docs`, the H2 console and all actuator endpoints except `health`; devtools is optional and excluded from the packaged jar |
| Enumeration | Random codes; per-client throttle on unknown-code lookups |

**Findings and actions**

1. **Fixed - expensive read not throttled.** The analytics endpoint scans a link's click rows and had no rate limit
   (only creates and unknown-code lookups were limited). Added a third per-client bucket
   (`app.rate-limit.analytics-per-minute`, default 30, local 300), with unit and integration tests.
2. **Fixed - vulnerable dependencies** (see K.3).
3. **Accepted / documented - default profile is `local`.** Forgetting `SPRING_PROFILES_ACTIVE=prod` silently runs on H2 with the H2 console and
   private targets enabled. Documented prominently in the README.
4. **Accepted / documented - rate limiting keys on `getRemoteAddr()`.** Prod sets `server.forward-headers-strategy: framework` so Ingress can supply the client IP. The Ingress must be the trusted hop.
5. **Accepted / documented - public analytics, no auth; open-redirect/phishing inherent to the product; best-effort click counts.**
